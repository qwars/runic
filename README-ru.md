# Runic

Легковесный движок для отображения HTML/CSS/JS виджетов на рабочем столе Linux. Современная альтернатива Conky с веб-стеком: пишите виджеты на привычных HTML, CSS и JavaScript, а Runic обеспечит интеграцию с системой через прозрачный IPC-мост.

Построен на **Rust + GTK3 + WebKitGTK + Layer Shell** (Wayland).

---

## Возможности

- **Настоящий веб-рендеринг** — HTML5, CSS3, современный JavaScript через WebKitGTK
- **Layer Shell интеграция** — виджеты располагаются под всеми окнами (или на других слоях)
- **Прозрачный фон** — виджеты органично вписываются в рабочий стол
- **Мощный IPC-мост** — 8 действий из коробки: чтение/запись файлов, выполнение команд, потоковый вывод, мониторинг файлов и управление потоками
- **Гибкое позиционирование** — размер, координаты, полноэкранный режим
- **Тихий режим** — по умолчанию не засоряет логи, отладка включается флагом `--debug`
- **Асинхронный стриминг** — вывод долгоиграющих команд поступает в виджет в реальном времени
- **Мониторинг файлов через inotify** — отслеживание изменений без опроса (нулевая нагрузка на CPU)
- **Hot-reload** — автоматическая перезагрузка виджета при изменении `.html`, `.css` или `.js` файлов (в режиме `--debug`)
- **Детектор выхода из сна** — автоматическая перезагрузка виджетов после пробуждения системы

## 🚀 Производительность (v1.3.0)

Проект оптимизирован для минимального потребления ресурсов:

| Метрика                   | Значение                 |
|---------------------------|--------------------------|
| Пиковая память при старте | ~30-50 МБ                |
| Количество потоков        | 8-12 (фиксированный пул) |
| CPU в простое             | <1%                      |
| Время отклика IPC         | <1 мс                    |
| Процессы-зомби            | Нет (Process Groups)     |

**ThreadPool**: фиксированный пул из 8 рабочих потоков обрабатывает все IPC-запросы. Устранено потребление ~800 МБ памяти и скачки нагрузки на планировщик ядра.

**Process Groups**: все команды `sh -c` запускаются в отдельной группе процессов. При завершении вся группа получает `SIGTERM`/`SIGKILL` — дочерние процессы (например, `tail -f`, `ping`) больше не остаются сиротами.

**Debouncing директорий**: временной debounce 500 мс предотвращает лавину inotify-уведомлений при самообращении скриптов в отслеживаемую директорию.

**Неблокирующие каналы**: `try_send` вместо `send_blocking` устраняет потенциальные deadlock'и при зависании GTK main loop.

**Монотонные часы**: `Instant` вместо `SystemTime` для детектора сна — корректная работа при переводе системных часов и NTP-синхронизации.

## 🛡️ Надёжность и безопасность (v1.3.0)

Проект проходит непрерывный аудит безопасности и стабильности:

- **Профилирование ресурсов**: встроенный сбор метрик использования памяти (VmRSS) и времени CPU (`getrusage`) для каждого IPC-запроса с логированием при превышении порогов.
- **Трекинг потоков (`ThreadTracker`)**: комплексный мониторинг активных и завершённых фоновых потоков — пиковое потребление памяти, время жизни и количество выполненных задач. Предотвращает незаметное исчерпание ресурсов.
- **Цветной вывод в консоль**: ANSI-цвета для мгновенного визуального распознавания типов сообщений: Ошибки (🔴), Предупреждения (🟡), Успех (🟢), Отладка (🔵) и Профилирование (🟣).
- **Атомарное управление процессами**: исключены состояния гонки (TOCTOU) при запуске потоковых команд. Повторный вызов `stream` с тем же аргументом гарантированно блокируется.
- **Безопасная очистка ресурсов**: устранена возможность двойного завершения процессов (double-kill) и паник при обработке сигналов `SIGTERM`/`SIGINT`. Все мьютексы защищены от "отравления" (poisoning).
- **Корректное завершение работы (Graceful Shutdown)**: все фоновые потоки получают сигнал остановки и завершаются чисто, не оставляя висячих процессов или утечек памяти.
- **Качество кода**: кодовая база полностью соответствует строгим проверкам `cargo clippy -- -D warnings` и включает 15 комплексных модульных тестов.

## Требования

- **ОС**: Linux с Wayland-композитором (Sway, Hyprland, Wayfire и т.п.)
- **Системные библиотеки**: GTK 3.24+, WebKitGTK 4.1, gtk-layer-shell
- **Rust**: 1.70+ (для сборки)

## Установка

### 1. Системные зависимости

**Debian 13 / Ubuntu:**

```bash
sudo apt install -y build-essential pkg-config libgtk-3-dev libwebkit2gtk-4.1-dev libgtk-layer-shell-dev
```

**Arch Linux:**

```bash
sudo pacman -S gtk3 webkit2gtk gtk-layer-shell
```

**Fedora:**

```bash
sudo dnf install gtk3-devel webkit2gtk4.1-devel gtk-layer-shell-devel
```

### 2. Сборка

```bash
git clone https://github.com/qwars/runic.git
cd runic
cargo build --release
```

Бинарник появится в `target/release/runic`.

## Использование

### Базовый запуск

```bash
# Виджет на весь экран (по умолчанию)
./target/release/runic examples/test.html/index.html

# Фиксированный размер 400x300 в левом верхнем углу
./target/release/runic examples/test.html/index.html -w 400 -H 300

# С отступом от краёв
./target/release/runic examples/test.html/index.html -w 400 -H 300 -x 50 -y 100

# Режим отладки
./target/release/runic examples/test.html/index.html --debug
```

### Параметры командной строки

| Параметр           | Описание                                                    | По умолчанию  |
|--------------------|-------------------------------------------------------------|---------------|
| `html_path`        | Путь к HTML-файлу виджета                                   | (обязательно) |
| `-w, --width <N>`  | Ширина окна в пикселях                                      | на весь экран |
| `-H, --height <N>` | Высота окна в пикселях                                      | на весь экран |
| `-x, --x <N>`      | Отступ от левого края                                       | 0             |
| `-y, --y <N>`      | Отступ от верхнего края                                     | 0             |
| `-d, --debug`      | Включить подробный вывод, цветные логи и статистику потоков | false         |

**Примечание**: координаты `-x` и `-y` работают только если задан размер окна (`-w` и `-H`).

### Автозапуск в Sway

Добавьте в `~/.config/sway/config`:

```
exec /home/user/runic/target/release/runic /home/user/runic/widgets/clock.html -w 300 -H 150 -x 50 -y 50
```

## API для виджетов

Runic предоставляет JavaScript-объект `window.ipc` для взаимодействия с системой.

### Отправка сообщения

```javascript
window.ipc.postMessage(
  JSON.stringify({
    action: "exec",
    payload: { command: "uname -a" },
  })
);
```

### Получение ответа

Определите глобальный обработчик:

```javascript
window.onRunicResponse = function (response) {
  // response.action  — имя действия
  // response.status  — "success" | "error" | "stream_data" | "watch_data"
  // response.message — текстовое сообщение
  // response.data    — полезные данные (строка или null)
  console.log(response);
};
```

### Доступные действия

#### `read` — чтение файла

```json
{ "action": "read", "payload": { "path": "/etc/os-release" } }
```

**Ответ**: `data` содержит содержимое файла.

#### `write` — дозапись в файл

```json
{ "action": "write", "payload": { "path": "/tmp/log.txt", "data": "строка\n" } }
```

**Примечание**: Родительские директории создаются автоматически. Файл открывается в режиме `append` (можно переопределить, передав `"append": false` в payload для очистки файла).

#### `exec` — выполнение команды

```json
{ "action": "exec", "payload": { "command": "df -h" } }
```

**Ответ**: `data` содержит `stdout` при успехе или `STDERR:\n...` при ошибке. Команда выполняется через `sh -c` с изоляцией в Process Group.

#### `stream` — потоковое выполнение

```json
{ "action": "stream", "payload": { "target": "ping -c 10 8.8.8.8" } }
```

**Ответ**: Приходит несколько раз, по одной строке за раз, со статусом `stream_data`. Идеально для `top`, `ping`, `tail -f` и других долгоиграющих команд. Повторный запуск той же команды блокируется, пока предыдущая не завершится.

#### `unstream` — остановка потокового выполнения

```json
{ "action": "unstream", "payload": { "target": "ping -c 10 8.8.8.8" } }
```

**Ответ**: Останавливает ранее запущенную команду `stream`. Вся Process Group получает `SIGKILL`, поток удаляется из списка активных.

#### `watch` — мониторинг файла через inotify

```json
{ "action": "watch", "payload": { "path": "/var/log/syslog", "tail": 10 } }
```

Отслеживает изменения в файле с помощью системного вызова `inotify` (нулевая нагрузка на CPU в ожидании событий). При каждом изменении файла новые строки отправляются в виджет со статусом `watch_data`.

- **Параметры**: `path` (обязательно), `tail` (опционально, количество последних строк файла, которые нужно отправить при старте).
- **Важно**: Повторный запуск `watch` для того же файла вернёт ошибку. Для остановки используйте действие `unwatch`.
- **Примечание**: Для чтения системных логов (`/var/log/syslog`, `/var/log/auth.log`) требуется членство в группе `adm`.

#### `unwatch` — остановка мониторинга файла

```json
{ "action": "unwatch", "payload": { "path": "/var/log/syslog" } }
```

**Ответ**: Останавливает мониторинг файла, запущенный ранее через `watch`. Поток inotify завершается, файловый дескриптор освобождается.

#### `stats` — статистика потоков

```json
{ "action": "stats" }
```

**Ответ**: Возвращает сводку по активным и завершённым потокам — пиковое потребление памяти, время жизни, количество выполненных задач.

## Режим отладки

Флаг `--debug` включает:

- **Вывод всех IPC-сообщений** в терминал с цветным форматированием.
- **Перенаправление `console.log`** из JS в stdout.
- **Информацию о размерах и позиционировании**.
- **Статистику потоков**: сводка по активным/завершённым потокам, памяти и CPU выводится в консоль каждые 30 секунд. Включает время жизни каждого потока в миллисекундах.
- **Hot-reload**: автоматическая перезагрузка виджета при изменении файлов `.html`, `.css`, `.js` в директории виджета (защита от дребезга — 300 мс).
- **Профилирование**: вывод метрик производительности при превышении порогов.
- **Расширенное логирование результатов выполнения**:
  - 🔵 `read`: путь, размер файла, превью содержимого (первые 100 символов), время выполнения
  - 🔵 `write`: путь, количество записанных байт, режим (добавление/перезапись), время выполнения
  - 🔵 `exec`: команда, код выхода, превью вывода (первые 200 символов), время выполнения
  - 🔵 `stream`: PID процесса, каждая строка из stdout/stderr, факт завершения с количеством прочитанных строк
  - 🔵 `watch`: тип объекта (файл/директория), данные из tail, каждое обнаруженное изменение, факт завершения с количеством событий
  - 🔵 `unstream`/`unwatch`: результат остановки с PID или путём

**Пример вывода в режиме отладки:**

```
[Руник ОТЛАДКА] Режим отладки включен
[Руник ОТЛАДКА] Обработчик 'ipc' зарегистрирован: true
[Руник ОТЛАДКА] Получено: {"action":"exec","payload":{"command":"uname -a"}}
[Руник ОТЛАДКА] exec запуск: 'uname -a'
[Руник РЕЗУЛЬТАТ] exec 'uname -a' => код выхода: Some(0), 15мс, вывод: 'Linux hostname 6.1.0...'
[Руник Профиль] 'exec' выполнен за 15ms | Память: 45200 KB | CPU: 120 ms
```

Запуск в режиме отладки:

```bash
cargo run -- examples/test.html/index.html --debug
```

**Важно**: В обычном режиме (без `--debug`) программа работает тихо — не выводит ничего в консоль и не отправляет ошибки в виджет (кроме критических ошибок запуска). Это позволяет использовать Runic в production без засорения логов.
